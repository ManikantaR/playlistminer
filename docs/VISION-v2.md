# PlaylistMiner — Vision v2: From Organizer to Learning Agent

> **Status:** Direction-setting document. Supersedes the *product framing* in `SPEC.md`
> (the technical spec stays valid as the data/infra foundation). This document defines
> *what we are actually building* and the phased path to get there.
>
> **Author/owner:** Mani (senior engineer — AI, C#, TypeScript, SQL, security)
> **Date:** 2026-06-14

---

## 1. The reframe

PlaylistMiner v1 was specced as a **playlist organizer**: a tool that sorts YouTube
bookmarks into topic folders. That answers *"where did I put that React video?"*

The real goal is a **personal learning agent** that answers a different question:
*"What concept should I learn next to stay sharp as a senior engineer focused on AI,
C#, TypeScript, SQL, and security?"*

These are different products. v2 keeps everything v1 built — OAuth, sync, the worker,
Postgres, the categorization pipeline architecture — but **re-casts them as the sensor
and actuator of a learning agent**, not the product itself.

> **One-line definition:** PlaylistMiner is a learning agent whose long-term memory is
> fed by my YouTube playlists. YouTube is one input source; the output is a living map
> of what I know, what I've watched, and what I should learn next.

## 2. The loop (what the user actually does)

```
   YouTube (I browse normally; YouTube's recommender is already good)
            │  I drop interesting videos into the "Incoming" playlist
            ▼
   ┌─────────────────────────────────────────────────────────┐
   │  PlaylistMiner = sensor + actuator                        │
   │                                                           │
   │  Quartz worker = the agent loop:                          │
   │   1. read Incoming                                        │
   │   2. local LLM (Ollama) understands each video            │
   │   3. file it → correct topic playlist   (silent)          │
   │   4. update mastery score per concept   (Postgres)        │
   │   5. rewrite the concept note           (markdown wiki)   │
   │   6. weekly: synthesize a learning plan                   │
   │                                                           │
   │  Postgres = ledger (facts)   markdown = story (judgments) │
   └──────────────────────────┬────────────────────────────────┘
                              │  MCP server facade
          ┌───────────────────┼───────────────┬──────────────┐
          ▼                   ▼               ▼              ▼
      Telegram bot       Home Assistant   OpenClaw /      Claude /
      (weekly push)      Voice (ask)      Hermes (orchestrate)  any MCP client
```

**Design principles** (from how the people Mani admires actually work):

- **Concepts, not links** (Karpathy). The agent nudges *what to learn*, not URLs — I can
  search YouTube myself, and YouTube's algorithm improves the more I lean in. The agent's
  durable output is an interlinked concept wiki, not a list of bookmarks.
- **It's what you ignore** (Hanselman). The system filters and protects attention. It
  nudges *less*, not more. Anything truly important reaches me multiple times.
- **Learn by building** (Osmani). Nudges should push toward active learning and gaps, not
  passive video-hoarding.

## 3. The brain — hybrid: Postgres for facts, markdown for narrative

The split rule: **Postgres owns facts the agent measures; markdown owns judgments the
agent makes.** Postgres is the *ledger*; the markdown wiki is the *story*. The story is
what gets read aloud and pushed to me.

| Postgres (the ledger — already built) | Markdown `concepts/` wiki (the story — new) |
|---|---|
| Videos, playlists, watch history, timestamps | `csharp.md`, `oauth.md`, `distributed-systems.md`, … |
| Mastery score per concept (a number, 0–100) | *Why* that score — what I've watched, what's next |
| Video → concept mappings | `[[wikilinks]]` between concepts = my skill graph |
| Quota, sync logs, undo log | Regenerated by the agent; hand-editable by me |

This is the **Karpathy LLM-Wiki pattern**: the wiki *is* the knowledge base. At personal
scale the whole concept set fits in one context window — no RAG, no vector DB. The schema
co-evolves: I refine the note template over time, the LLM fills it in. Because it's plain
markdown in git, `git log` becomes a literal history of my learning.

**Concept note template (draft):**

```markdown
---
concept: oauth
category: security
mastery: 35          # 0-100, computed from watch history + manual signal
status: learning     # unknown | learning | competent | expert
updated: 2026-06-14
---

# OAuth 2.0

## What I know
<agent-maintained summary of what I've already watched/understood>

## Watched
- [[video:abc123]] — "OAuth deep dive" (watched 2026-06-10)

## Gaps / next
- PKCE flow for public clients
- Token rotation + refresh token theft detection

## Related
[[oidc]] · [[jwt]] · [[api-security]]
```

## 4. Understanding videos — local LLM (Ollama)

Replace the v1 keyword + TF-IDF categorizer with a local LLM that reads each video's
title, description, and (when available) transcript, then: (a) picks the target playlist,
(b) extracts concepts, (c) updates mastery and the concept note.

**Model choice for the 16GB M1 Mac** (mid-2026 benchmarks):

| Model | Why | When |
|---|---|---|
| **Qwen 3.5 ~8B (Q4, ~5GB)** | Best quality-per-GB for summarization + light reasoning; fits fully in memory; fast | **Default** |
| Gemma 4 E4B | Lighter/faster fallback | If running other things alongside |
| Mistral Small 3 (24B, Q3) | Highest summarization correctness (~80%) | Overnight batch only — spills on 16GB, too slow interactive |

**Rule:** prefer the model that fits *entirely* in memory (Qwen 8B). A model that spills
to system RAM runs 5–10× slower. Heavy weekly synthesis runs as a scheduled overnight job,
so model size matters less there.

The v1 keyword/TF-IDF code is **not deleted** — it stays as a cheap fast-path / fallback
when Ollama is unavailable.

## 5. Nudge policy — weekly heartbeat, daily only if actionable

What I "should learn" doesn't change day-to-day, so a daily nudge trains me to ignore it.

- **Continuous & silent:** Incoming → topic playlist filing. No notification.
- **Weekly (the real one):** agent reads the whole wiki + the week's watch history and
  produces **one** focused learning plan — the gap, why it matters, and which already-filed
  videos start closing it. Pushed to **Telegram**; readable aloud via **Home Assistant Voice**.
- **Daily:** fires *only* on a concrete trigger (e.g., I started a series and there's a
  clear next episode). Otherwise silent.

**Delivery channels** are just clients of the agent:
- **Telegram bot** = push channel (free, simple API, on my phone).
- **Home Assistant Voice** = pull channel ("what should I learn today?" → reads latest plan).

## 6. Runtime + interop — Quartz loop + MCP server facade

- **The agent loop lives in the existing Quartz worker** — C#, full control, no new stack.
  It does steps 1–6 of the loop in §2.
- **Add a thin MCP server facade** exposing the agent's capabilities as tools. This is the
  2026 standard for agent interop and is what lets *my other personal agents talk to it*.

I don't build "an agent that talks to OpenClaw/Hermes." I build a **capability OpenClaw or
Hermes can call.** Telegram and HA Voice then come almost for free — they hit the same MCP
tools.

**Proposed MCP tools (draft surface):**

| Tool | Purpose |
|---|---|
| `get_learning_plan()` | Return the current weekly plan |
| `whats_next(topic?)` | Next concept to learn, optionally scoped to a topic |
| `list_gaps()` | Concepts where mastery is low but relevance is high |
| `record_watched(videoId)` | Mark a video watched; updates mastery |
| `get_concept(name)` | Return a concept note |
| `list_incoming()` | What's queued and unfiled |
| `trigger_organize()` | Run the filing pass on demand |

## 7. Phased roadmap (each phase reuses what exists)

> **Hard rule: do not build Phases 1–4 until Phase 0 works end-to-end with real
> playlists.** The most common failure mode for a vision this good is building the brain
> before the hands work. Right now OAuth has not been tested with live credentials and a
> "failed to trigger sync" issue is still open.

### Phase 0 — Make the hands work (now)
- Verify OAuth Connect flow end-to-end with live Google credentials.
- Confirm sync actually fills the DB from real playlists.
- Resolve the "failed to trigger sync" issue (NEXT_PUBLIC_API_URL build-arg fix deployed).
- Designate an **Incoming** playlist (the inbox).
- **Exit criteria:** I can connect YouTube, sync, and see my real videos in the app.

### Phase 1 — Understanding + the brain
- Swap keyword/TF-IDF → Ollama (Qwen 8B) for video understanding (keep old path as fallback).
- Add `concepts/` markdown wiki + concept-note template.
- Add `mastery` + video→concept mapping to Postgres.
- Silent filing: Incoming → topic playlists, with the 7-day undo already built.
- **Exit criteria:** I drop a video in Incoming; it gets filed and a concept note updates.

### Phase 1.5 — Deploy to the NAS (prerequisite for always-on)
- Convert `podman-compose.yml` → `docker compose` on the NAS; adapt `deploy-to-nas.sh`.
- Bootstrap OAuth on the Mac → copy encrypted token row to NAS Postgres (see NAS spec §4).
- Wire Traefik route, Uptime Kuma monitor, Homepage card, daily backup.
- Worker points `Ollama__BaseUrl` at the Mac; graceful queue + "Process now" trigger.
- **Exit criteria:** the agent runs 24/7 on the NAS and files Incoming whenever the Mac is up.

### Phase 2 — Weekly synthesis + push
- Quartz job: weekly synthesis reads wiki + watch history → learning plan.
- Telegram bot delivers the weekly plan.
- **Exit criteria:** Every week I get one useful, low-noise learning nudge on Telegram.

### Phase 3 — MCP facade + interop
- Expose the MCP server facade (tools in §6).
- Wire Home Assistant Voice as a pull client.
- Confirm OpenClaw/Hermes can call the tools.
- **Exit criteria:** I can ask my other agent / HA Voice "what should I learn next?"

### Phase 4 — Outbound (the original "Phase 2" idea)
- Agent looks at *who* I follow (Hanselman, Osmani, Karpathy, Chapsas, …) and surfaces
  *concepts* worth learning from them — still concepts, not a firehose of URLs.
- **Exit criteria:** The agent suggests learning directions I wouldn't have found myself.

## 7b. Deployment — UGREEN NAS (Docker), inference on the Mac

Full detail in `docs/NAS-DEPLOYMENT-SPEC.md`; ADR-009 records the decision. Summary:

- **Always-on tier on the NAS:** `pm-db`, `pm-api`, `pm-worker`, `pm-web` run as **Docker**
  containers on the UGREEN DXP4800+ (UGOS), behind Traefik at
  **`https://playlistminer.home.manikantar.com`** (wildcard Let's Encrypt TLS),
  inheriting the homelab stack and `deploy-to-nas.sh` pattern. Podman stays for Mac dev only.
- **Inference on the Mac:** Ollama (Qwen ~8B) runs on the M1 Mac, not the N100 NAS. The
  worker calls `Categorization__OllamaBaseUrl=http://<MAC_IP>:11434` and **degrades
  gracefully** — when the Mac sleeps, videos wait in Incoming and a **"Process now"** button
  / `POST /api/agent/process-now` lets you drain the queue on demand.
- **OAuth:** completes **directly on the NAS** (real HTTPS domain) — register
  `https://playlistminer.home.manikantar.com/api/oauth/callback` in Google Console and
  publish the consent screen. An API key can't touch private playlists, so OAuth is
  required. Mac-localhost + token-copy is the fallback.

```
   Mac (M1)                         NAS (UGREEN, always-on, Docker)
   ┌─────────────┐                  ┌───────────────────────────────┐
   │ Ollama      │◄─── LAN HTTP ────│ pm-worker (agent loop)         │
   │ Qwen ~8B    │  graceful queue  │ pm-api · pm-web · pm-db        │
   └─────────────┘  + Process-now   │ Traefik 443 (HTTPS) · backups │
                                    └───────────────────────────────┘
              https://playlistminer.home.manikantar.com (OAuth works here)
```

## 8. What changes vs. v1 (and what doesn't)

**Keep as-is:** OAuth + YouTube API integration, sync service, Quartz worker, Postgres
schema, watch/undo/backup/quota infrastructure, CI/CD, testing approach, Podman setup.

**Re-cast:** the categorization pipeline becomes "video understanding"; topic playlists
become the *actuator* of the agent, not the product.

**Add:** `concepts/` markdown wiki, mastery model, Ollama understanding, weekly synthesis
job, MCP server facade, Telegram + HA Voice clients.

**Drop:** the framing that this is a "playlist organizer." It's a learning agent.

## 9. Open questions (to revisit, not blockers)

- **Watch-history source:** YouTube API doesn't expose watch history. Options: track clicks
  from within the app, periodic Google Takeout import, or infer from playlist moves. Decide
  in Phase 1.
- **Mastery scoring formula:** how watch time, rewatches, and manual signal combine into the
  0–100 score. Start crude (watched = +N), refine.
- **Transcript access:** how to get transcripts cheaply (yt-dlp captions vs API) for better
  understanding. Optional in Phase 1.
